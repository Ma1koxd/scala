# Лабораторная работа: планировщик личной нагрузки

# Вариант 8

## Общая идея

Разработать консольное приложение, которое помогает пользователю составить реалистичный план выполнения дел.

Пользователь задаёт:

* дела, которые необходимо выполнить;
* трудоёмкость каждого дела;
* дату, начиная с которой дело можно выполнять;
* срок выполнения;
* приоритет;
* возможность деления дела на части;
* свободные временные интервалы.

Программа должна распределить оставшуюся трудоёмкость дел по указанным пользователем свободным временным интервалам.

Свободное время задаётся пользователем напрямую. Программа не должна автоматически рассчитывать его на основе сна, питания, учёбы, работы и других занятий.

Для каждой задачи используются собственные дата начала и срок выполнения. Отдельный общий период планирования не задаётся.

При построении расписания пользователь указывает текущую дату. Она используется для определения просроченных дел и исключения уже прошедших свободных интервалов.

Если все дела невозможно полностью разместить, программа не должна нарушать заданные ограничения. Неразмещённые и просроченные дела должны быть показаны пользователю отдельно.

---

# 1. Работа с приложением

Приложение должно управляться через текстовое нумерованное меню.

Пользователь должен иметь возможность:

* добавлять дела;
* просматривать список дел;
* изменять дела;
* удалять дела;
* отменять дела;
* добавлять свободные временные интервалы;
* просматривать свободные временные интервалы;
* удалять свободные временные интервалы;
* составлять расписание;
* повторно составлять расписание после изменения исходных данных;
* просматривать построенное расписание;
* отмечать выполненную часть дела;
* просматривать просроченные дела;
* просматривать дела, которые не удалось разместить;
* сохранять текстовый отчёт;
* перезагружать конфигурацию;
* завершать работу.

Типичный сценарий работы:

1. Пользователь добавляет необходимые дела.
2. Для каждого дела указывает трудоёмкость, дату начала, срок, приоритет и возможность деления.
3. Пользователь добавляет интервалы свободного времени.
4. При построении расписания пользователь указывает текущую дату.
5. Программа распределяет оставшуюся трудоёмкость дел по подходящим свободным интервалам.
6. Пользователь получает общее расписание.
7. По мере выполнения пользователь отмечает прогресс.
8. После изменения дел, прогресса или свободного времени расписание можно построить заново.

---

# 2. Дела пользователя

Каждое дело должно содержать:

* уникальный идентификатор;
* название;
* общую трудоёмкость в часах;
* уже выполненное количество часов;
* дату, начиная с которой дело можно выполнять;
* срок завершения;
* приоритет;
* возможность деления на части;
* минимальную продолжительность одного блока для делимой задачи;
* состояние.

Описание дела отдельно не используется.

Возможные состояния:

* PLANNED — запланировано;
* IN_PROGRESS — выполняется;
* COMPLETED — завершено;
* OVERDUE — просрочено;
* CANCELLED — отменено;
* UNPLACED — не удалось разместить.

Пример дела:

```text
ID: 1
Название: Курсовой проект
Трудоёмкость: 18 часов
Выполнено: 3 часа
Осталось: 15 часов
Можно начать: 10 сентября
Срок: 25 сентября
Приоритет: HIGH
Можно делить: да
Минимальный блок: 60 минут
Состояние: IN_PROGRESS
```

Трудоёмкость пользователь задаёт самостоятельно.

Программа не должна автоматически определять трудоёмкость по названию дела.

Оставшаяся трудоёмкость рассчитывается как:

```text
оставшаяся трудоёмкость =
общая трудоёмкость - уже выполненная трудоёмкость
```

Если выполнено 0 часов, дело имеет состояние PLANNED.

Если выполнено больше 0 часов, но меньше общей трудоёмкости, дело имеет состояние IN_PROGRESS.

Если выполненная трудоёмкость равна общей, дело имеет состояние COMPLETED.

Пользователь может отменить незавершённое дело. В этом случае оно получает состояние CANCELLED и больше не участвует в построении расписания.

Уже завершённое дело отменять нельзя.

## Делимые дела

Если дело допускает деление, его можно распределить по нескольким свободным интервалам.

Например:

```text
Осталось выполнить: 5 часов

15 сентября — 2 часа
16 сентября — 1 час
18 сентября — 2 часа
```

Продолжительность обычного блока не должна быть меньше установленного минимального размера.

Последний блок может быть меньше минимального размера, если оставшаяся трудоёмкость меньше установленного минимума.

## Неделимые дела

Если дело нельзя разделять, вся его оставшаяся трудоёмкость должна быть помещена в один непрерывный свободный интервал.

Например, неделимое дело продолжительностью 3 часа нельзя разместить в трёх отдельных интервалах по одному часу.

---

# 3. Свободное время

Свободное время пользователь задаёт непосредственно.

Для каждого свободного интервала задаются:

* дата;
* время начала;
* время окончания.

Пример:

```text
Дата: 20 сентября
Начало: 15:00
Окончание: 18:00
```

Время окончания должно быть позже времени начала.

Один свободный интервал относится только к одной календарной дате.

Переход свободного интервала через полночь не используется.

Например, допустимо:

```text
20 сентября
18:00–22:00
```

Но не используется интервал:

```text
20 сентября
23:00–02:00
```

Пересекающиеся свободные интервалы одной даты добавлять нельзя.

Например, интервалы:

```text
10:00–12:00
11:00–13:00
```

пересекаются и не должны одновременно сохраняться.

Соседние интервалы разрешены:

```text
10:00–12:00
12:00–14:00
```

Пользователь должен иметь возможность:

* добавлять свободное время;
* просматривать свободное время;
* удалять свободное время.

После добавления или удаления свободного времени ранее построенное расписание считается устаревшим.

Программа не использует:

* регулярные занятия;
* разовые занятые события;
* автоматическое размещение сна, питания и других занятий;
* готовый шаблон распорядка пользователя.

---

# 4. Правила построения расписания

Перед построением расписания пользователь вводит текущую дату.

Текущая дата используется для:

* определения просроченных дел;
* исключения свободных интервалов, относящихся к уже прошедшим датам.

При построении расписания дело может быть размещено только:

* не раньше собственной даты начала;
* не позже собственного срока;
* в свободном временном интервале;
* с учётом возможности деления;
* с учётом минимального размера блока;
* без пересечения с уже размещёнными блоками.

Отдельный глобальный период планирования не используется.

Для каждого дела его допустимый период определяется собственными полями:

```text
дата начала → дедлайн
```

## Порядок обработки дел

Порядок обработки должен быть детерминированным.

Дела сортируются:

1. по ближайшему сроку;
2. при одинаковом сроке — по более высокому приоритету;
3. при одинаковом сроке и приоритете — по порядку добавления, то есть по меньшему идентификатору.

Дополнительный расчёт «запаса свободного времени» не используется.

Пример:

```text
Дело A:
дедлайн 20 сентября
приоритет LOW

Дело B:
дедлайн 25 сентября
приоритет CRITICAL
```

Первым рассматривается дело A, так как его срок наступает раньше.

Если сроки совпадают:

```text
Дело A:
дедлайн 20 сентября
приоритет LOW

Дело B:
дедлайн 20 сентября
приоритет CRITICAL
```

первым рассматривается дело B.

## Раннее выполнение

Используется один режим построения расписания — раннее выполнение.

Для каждого дела выбираются наиболее ранние подходящие свободные интервалы.

Отдельный режим равномерного распределения нагрузки не используется.

## Размещение неделимого дела

Для неделимого дела программа ищет самый ранний подходящий свободный интервал, в который полностью помещается оставшаяся трудоёмкость.

Если такого интервала нет, дело получает состояние UNPLACED.

## Размещение делимого дела

Для делимой задачи программа последовательно использует наиболее ранние подходящие свободные интервалы.

Размещение продолжается, пока не будет распределена вся оставшаяся трудоёмкость.

Если всю оставшуюся трудоёмкость разместить невозможно, временно созданные блоки этой задачи не сохраняются.

В таком случае:

* задача получает состояние UNPLACED;
* использованные при попытке размещения интервалы возвращаются;
* ранее успешно размещённые другие задачи остаются в расписании.

## Завершённые и отменённые дела

Дела со состоянием COMPLETED и CANCELLED не участвуют в построении расписания.

## Просроченные дела

Если:

* оставшаяся трудоёмкость больше нуля;
* дедлайн находится раньше текущей даты;
* дело не является COMPLETED или CANCELLED;

дело получает состояние OVERDUE.

Просроченное дело не размещается в расписании.

---

# 5. Использование свободного времени

При успешном размещении блока занятая часть свободного интервала удаляется из доступного времени.

Если использован только фрагмент интервала, оставшаяся часть должна сохраниться.

Например:

```text
Свободно:
10:00–15:00

Размещено дело:
10:00–13:00
```

После размещения должно остаться:

```text
13:00–15:00
```

Если свободный интервал использован полностью, он удаляется из списка оставшегося свободного времени.

При повторном построении расписания программа должна использовать исходные свободные интервалы пользователя, а не интервалы, оставшиеся после предыдущего построения.

Таким образом, расписание каждый раз строится заново на основе актуальных исходных данных.

Максимальная дневная нагрузка отдельно не используется.

Обязательные перерывы отдельно не рассчитываются.

Резерв времени не используется.

Пользователь самостоятельно определяет допустимую нагрузку тем, какие свободные интервалы он добавляет.

---

# 6. Представление расписания

Пользователь должен иметь возможность просматривать общее построенное расписание.

Для каждого блока выводятся:

* идентификатор дела;
* дата;
* время начала;
* время окончания;
* продолжительность.

Пример:

```text
Расписание:

ID задачи: 1
Дата: 2026-09-15
Начало: 10:00
Окончание: 12:00
Продолжительность: 120 минут

ID задачи: 2
Дата: 2026-09-15
Начало: 12:00
Окончание: 15:00
Продолжительность: 180 минут
```

Отдельно должны выводиться:

* просроченные дела;
* неразмещённые дела;
* оставшиеся после построения свободные интервалы.

Отдельные режимы просмотра:

* на день;
* на неделю;
* только выбранного дела

не используются.

Все даты и время уже показываются в общем расписании.

Отдельный список дней с высокой нагрузкой также не используется.

---

# 7. Обнаружение невозможного плана

Если все дела невозможно разместить, программа не должна автоматически нарушать сроки или другие ограничения.

Неразмещённое дело получает состояние UNPLACED.

Программа должна показать:

* какие дела не удалось разместить;
* оставшуюся трудоёмкость каждого такого дела;
* срок каждого такого дела;
* суммарное количество неразмещённой работы.

Пример:

```text
План построен не полностью.

Не удалось разместить задач: 2
Не размещено работы: 4.5 часа

Не размещены:

Курсовой проект
Осталось: 3 часа
Срок: 25 сентября

Подготовка доклада
Осталось: 1.5 часа
Срок: 27 сентября
```

Следует использовать формулировку «неразмещённая работа», а не обязательно «дефицит свободного времени».

Например, неделимое дело продолжительностью 3 часа может не разместиться даже при наличии трёх отдельных свободных интервалов по одному часу.

В таком случае суммарного времени достаточно, но отсутствует один непрерывный подходящий интервал.

Программа не должна самостоятельно:

* изменять срок дела;
* изменять его трудоёмкость;
* менять приоритет;
* делать неделимую задачу делимой;
* отменять дело.

---

# 8. Учёт выполнения

Пользователь должен иметь возможность отмечать прогресс выполнения дела.

Пользователь указывает:

* идентификатор дела;
* сколько дополнительных часов было выполнено.

Например:

```text
Дело: Курсовой проект

Было выполнено: 3 часа
Добавлено: 2.5 часа
Всего выполнено: 5.5 часа
Осталось: 12.5 часа
```

Выполненная трудоёмкость:

* не может быть отрицательной;
* не может превышать общую трудоёмкость.

Если после обновления прогресса выполненная трудоёмкость становится равна общей, дело получает состояние COMPLETED.

Если выполнено больше нуля, но меньше общей трудоёмкости, дело получает состояние IN_PROGRESS.

После изменения прогресса текущее расписание считается устаревшим.

При следующем построении программа должна использовать только оставшуюся трудоёмкость:

```text
общая трудоёмкость - выполненная трудоёмкость
```

Свободные интервалы с датой раньше введённой текущей даты не используются.

Отдельная команда «день стал недоступен» не используется.

Если пользователь больше не располагает временем в определённый день, он должен удалить соответствующий свободный интервал и заново построить расписание.

---

# 9. Перестроение расписания

Расписание строится на основе актуальных:

* дел;
* выполненной трудоёмкости;
* состояний дел;
* свободных временных интервалов;
* текущей даты.

После изменения:

* дела;
* трудоёмкости;
* выполненных часов;
* даты начала;
* срока;
* приоритета;
* возможности деления;
* минимального блока;
* состояния дела;
* свободного времени

старое расписание считается недействительным.

При следующем построении расписание формируется заново.

Построенное расписание не является основными сохраняемыми данными приложения.

---

# 10. Конфигурационный файл

Программа должна использовать отдельный конфигурационный файл.

Конфигурация содержит технические пути к файлам приложения.

Пример:

```json
{
  "logFile": "planner.log",
  "stateFile": "planner-state.json",
  "reportDirectory": "reports"
}
```

В конфигурации задаются:

* путь к файлу журнала;
* путь к файлу состояния;
* каталог для текстовых отчётов.

Параметры, которые не используются программой, не должны присутствовать в конфигурации.

В частности, не используются настройки:

* режима равномерного распределения;
* регулярных занятий;
* резервов;
* максимальной дневной нагрузки;
* обязательных перерывов;
* автоматического размещения питания.

Пользователь должен иметь возможность перезагрузить конфигурацию без перезапуска приложения.

Если новая конфигурация некорректна, программа должна сообщить об ошибке и продолжить использовать последнюю корректную конфигурацию.

Если корректная конфигурация ещё не была загружена, могут использоваться значения путей по умолчанию.

---

# 11. Сохранение состояния

Исходные данные должны сохраняться между запусками программы.

Необходимо сохранять:

* список дел;
* их идентификаторы;
* общую трудоёмкость;
* выполненную трудоёмкость;
* даты начала;
* сроки;
* приоритеты;
* возможность деления;
* минимальные блоки;
* состояния;
* свободные временные интервалы.

После повторного запуска программы идентификаторы новых дел должны оставаться уникальными.

Для этого программа может:

* сохранять значение следующего идентификатора;
* либо вычислять его на основе уже существующих дел.

Готовое расписание между запусками программы не сохраняется.

После загрузки состояния пользователь при необходимости строит расписание заново.

Это позволяет избежать ситуации, когда сохранённое расписание перестало соответствовать изменённым исходным данным.

Программа должна корректно обрабатывать:

* отсутствие файла состояния;
* повреждённый файл состояния;
* невозможность прочитать файл;
* невозможность записать файл.

Ошибка сохранения или загрузки не должна приводить к аварийному завершению приложения.

---

# 12. Текстовый отчёт

Пользователь должен иметь возможность создать текстовый отчёт.

Отчёт должен содержать:

* список дел;
* их состояния;
* общую трудоёмкость;
* выполненную трудоёмкость;
* оставшуюся трудоёмкость;
* построенное расписание;
* список просроченных дел;
* список не размещённых дел;
* суммарное количество не размещённой работы;
* оставшиеся свободные интервалы.

Отдельный глобальный период планирования в отчёте не используется.

Даты уже содержатся:

* в самих делах;
* в свободных интервалах;
* в блоках построенного расписания.

Отчёт сохраняется в каталог, указанный в конфигурации.

Если отчёт создать невозможно, программа должна вывести понятное сообщение об ошибке и продолжить работу.

---

# 13. Журналирование

Приложение должно вести журнал своей работы.

В журнал необходимо записывать основные действия:

* запуск программы;
* завершение программы;
* загрузку конфигурации;
* перезагрузку конфигурации;
* загрузку состояния;
* сохранение состояния;
* добавление дела;
* изменение дела;
* удаление дела;
* отмену дела;
* изменение прогресса;
* добавление свободного интервала;
* удаление свободного интервала;
* начало построения расписания;
* завершение построения расписания;
* обнаружение просроченного дела;
* обнаружение неразмещённого дела;
* создание отчёта;
* ошибки чтения и записи файлов;
* внутренние ошибки программы.

В журнале не требуется сохранять все данные дела целиком.

Допускается записывать:

* идентификатор дела;
* дату;
* продолжительность;
* новое состояние;
* результат операции;
* причину ошибки.

Файл журнала задаётся в конфигурации.

# 14. Проверка данных и обработка ошибок

Программа должна проверять вводимые данные.

## Проверка дела

Необходимо обнаруживать:

* отрицательную или нулевую трудоёмкость;
* отрицательное количество выполненных часов;
* выполненное время, превышающее общую трудоёмкость;
* срок, находящийся раньше даты начала;
* неизвестный приоритет;
* неположительный минимальный блок для делимой задачи.

Некорректное значение должно запрашиваться повторно сразу после ввода, а не после заполнения всех остальных полей дела.

## Проверка свободного времени

Необходимо обнаруживать:

* время окончания, которое не позже времени начала;
* пересекающиеся интервалы одной даты;
* неправильный формат даты;
* неправильный формат времени.

Соседние интервалы не считаются пересекающимися.

Например:

```text
10:00–12:00
12:00–14:00
```

допустимы.

## Проверка числового ввода

Если вместо числа введено некорректное значение, программа не должна аварийно завершаться.

Она должна вывести сообщение об ошибке и предложить ввод повторно.

## Обработка отсутствия данных

Программа должна корректно работать, если:

* список дел пуст;
* список свободного времени пуст;
* расписание пусто;
* ни одно дело не удалось разместить.

## Изменение исходных данных

После изменения дела или свободного времени построенное ранее расписание должно считаться устаревшим.

При необходимости пользователь строит его заново.

## Ошибки файлов

Необходимо корректно обрабатывать:

* отсутствие конфигурационного файла;
* повреждённый конфигурационный файл;
* отсутствие файла состояния;
* повреждённый файл состояния;
* невозможность прочитать файл;
* невозможность записать состояние;
* невозможность создать журнал;
* невозможность создать отчёт.

Ошибки файлов не должны приводить к неконтролируемому завершению программы.

# 15. Ограничения задания

В рамках лабораторной работы не требуется:

* синхронизироваться с Google Calendar или другими календарями;
* отправлять уведомления;
* работать в фоновом режиме;
* автоматически определять трудоёмкость дел;
* оценивать психологическое или физическое состояние пользователя;
* давать медицинские рекомендации;
* автоматически менять сроки;
* самостоятельно отменять дела;
* отслеживать активность пользователя;
* реализовывать полноценный календарный сервер;
* создавать графический интерфейс;
* использовать внешние API.
